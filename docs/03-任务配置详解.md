# 03 · 任务配置详解

> 所有任务配置都在**任务页**里改，保存后写进 `data/config/tasks.json`。
> 环境变量（`.env`）只是**没有该文件时**的兜底 —— 两边不一致时以 `tasks.json` 为准。

## 1. 触发时间

| 项 | 说明 |
|---|---|
| 小时 / 分钟 | 例如 09:30 |
| 时区 | 固定 `Asia/Shanghai`，不随服务器时区变化 |
| 抖动（jitter） | 设了 N 分钟，就在整点后随机延后 0~N 分钟再发 |

**为什么要有抖动**：不设的话每天 09:30:00 准点发出，时间戳整齐得不像人。
想要"看起来像手打的"，设个 5~25 分钟。

> 环境变量兜底：`HUOHUA_SCHEDULE_HOUR` / `HUOHUA_SCHEDULE_MINUTE`（默认 10:30）。

## 2. 发送间隔

每发给一个人之后，停顿一段**随机时长**再发下一个：

```
HUOHUA_SEND_GAP_MIN_SEC=20
HUOHUA_SEND_GAP_MAX_SEC=90
```

也可以在任务页里配。**别调太小** —— 秒级连发很容易触发平台风控。

## 3. 轮换策略（rotation）

决定一次运行里**给哪些人发**：

| 值 | 行为 |
|---|---|
| `all` | 给所有**已启用**的收件人都发（默认） |
| `round_robin` | 轮流：这次发一部分，下次从上次的位置接着发 |
| `random` | 随机挑一个 |

火花场景一般就用 `all`（每天都得发，不能漏人）。

## 4. 文案池（messages）

可以放多条，每次发送**随机挑一条**。

每条的 `kind` 有四种：

| kind | 含义 | 必填字段 |
|---|---|---|
| `text` | 纯文字 | `content` |
| `image` | 图片 | `path`（本地路径） |
| `sticker` | 表情 | `sticker` |
| `random` | 在这条的 `choices` 里再随机选一个 | `choices` |

示例（`data/config/tasks.json` 的片段）：

```json
{
  "messages": [
    { "kind": "text", "content": "早" },
    { "kind": "text", "content": "1" }
  ]
}
```

> 💡 **恒定文案要特别注意确认逻辑**：如果每天都发同样的内容（比如"1"），
> 会话列表的预览看起来就不会变。工具改用「**消息区里这条内容的行数**是否增加」来判断，
> 所以恒定文案也能确认 —— 但偶尔仍会返回「结果不确定」，见 [05 · 故障排查](05-故障排查.md#发送)。

## 5. 收件人

- 在**收件人页**点「同步好友列表」拉取，**手动打开**要发的人的开关；
- 新同步进来的人**默认是关闭的**（刻意如此，避免误发）；
- 收件人名单存在 `data/config/contacts.json`。

## 6. 演练模式

两种方式：

- 任务页 / 首页勾选「**演练**」；
- 环境变量 `HUOHUA_DRY_RUN=true`。

演练会完整走一遍（选人、开会话、找输入框），但**不点发送** —— 对好友零影响。
**第一次配置完、或改过选择器 / 抖音页面变了之后，都建议先跑一次演练。**

## 7. 失败重试

| 项 | 默认 | 说明 |
|---|---|---|
| `MAX_RETRIES` | 3 | 单个人最多重试几次 |
| `RETRY_BACKOFF_SEC` | 30 | 重试之间等多久 |
| `RISK_COOLDOWN_SEC` | 300 | 命中风控标记后冷却多久 |

> ⚠️ **「结果不确定」不会重试** —— 它的含义是"消息**可能已发出**"，
> 重试就是重复发送。这是本工具最不能犯的错。

## 8. 定时任务没跑？

先查 `/api/system/overview` 里的 `next_run_at` 和 `job_count`（正常是 **2**：发送 + 每日汇总），
再看 [05 · 故障排查](05-故障排查.md#定时任务)。
