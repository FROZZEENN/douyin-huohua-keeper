## 二、已确认但**本轮未修**（按优先级，含建议）

### P0 · 安全

1. **`account_id` / `run_id` 未做校验，可路径穿越**
   `routes/accounts.py`、`routes/runs.py` 直接把请求参数拼进路径。
   `account_id=..\..\x` 可能越出 `data_dir`，影响 `DELETE /state`、`qr_start`（可写文件）、读 report。
   建议：`^[A-Za-z0-9_-]{1,64}$` 白名单校验 + `Path.resolve()` 后确认仍在允许目录内。
2. **500 响应回显异常原文**（`app.py` 的全局 handler）
   `type(exc).__name__: exc` 会泄露本机路径与实现细节。建议只回笼统提示，细节仅进日志。
3. **`?token=` 会留在浏览器历史 / Referer / 访问日志**，且令牌校验无退避。
   建议：校验失败加简单退避；文档里说明 `?token=` 仅用于首次打开。

### P1 · 功能正确性

4. **`engine/sender.py` 未捕获 `BrowserError`**
   `session.call(...)` 抛出的 `BrowserError` 直接穿透 `send_to_contact`，违反"失败一律返回 `SendOutcome`"的契约 → 会让异常走到 runner 的兜底 `except`，丢失逐人失败分类。
   建议：包一层 try/except，转成 `SendOutcome(FAILED, kind=TRANSIENT/UNKNOWN)`。
5. **`engine/confirmer.py` 的失败标记过宽**
   `MESSAGE_FAILED` 含 `[class*="failed"]` / `[class*="error"]`，无关元素命中即判 FAILED(TRANSIENT) → 触发重试 → **可能重复发送**（本工具最不能出的错）。
   建议：收紧到发送气泡内的具体标记；并把"未能确认"与"明确失败"分开——前者不该重发。
6. **`navigator.search_conversation` 返回的 `index` 语义不一致**
   它是"搜索结果序号"，却被 `open_conversation` 当作"会话列表行号"用于点击 → 会点开另一个人（仅靠头部名字校验兜住）。
   目前 `runner` 恒传 `allow_search=False`，生产不可达，但这是一颗定时炸弹。
7. **`engine` 层存在两套错误分类**（`errors.classify` 与 `sender` 内部映射）
   同一句"找不到输入框"在两处分别被判为 TRANSIENT 与 AUTH。建议只保留一处。

### P2 · 性能（按收益排序）

8. ✅ **已修** —— `async def` 路由里做同步阻塞调用，会冻结整个事件循环。
   10 个含阻塞调用的路由改成同步 `def`（FastAPI 自动丢进线程池）：
   `contacts.sync/discovered/friends`、`accounts.qr_start/qr_poll/qr_cancel/logout`、
   `system.check/notify_test`、`runs.trigger_now`。
   **实测**：6.5s 的浏览器操作期间，`/api/health` 136 次请求最大延迟仅 **19ms**（修复前 ≈ 重操作耗时）。
9. ⬜ `confirmer` 每 0.4s 全量重读会话列表（`read_conversation_list(40)`，每行约 20 次选择器查询）只为取一个 preview。
   建议：只查目标行；或改用 `[data-e2e]` 定位 + 局部读取。

   > 📌 **决定：暂缓（2026-09-19 补记）**。实测每次确认耗时 **1.4~3.9 秒**，远低于 15 秒的确认预算 —— 也就是说
   > 这个开销**当前没有造成用户可见的问题**。而优化它要改的是**「这条到底发出去没有」的判定路径**，
   > 那正是本项目最不能出错的地方（判定错了 = 少发 或 重复发）。
   > 权衡下来：**等定时任务在真实环境跑顺了再做**，届时先加针对性测试（`_read_entry_for` 的快路径），
   > 且必须保留「名字对不上就回退到全量扫描」的兜底。10. ⬜ `navigator` 一行会话几十次选择器 round-trip（名字 / 预览 / 火花 / 头像 / 群判定各自独立查询）。
    建议：一次 `evaluate()` 在页面里把需要的字段一起抠出来，往返次数从几十降到 1。
11. ⬜ `routes/runs.py` 的 `/api/runs` 逐条读 report.json（最多 500 个，N+1）+ `repo` 里 contacts/streak/index 的读-改-写每次全量。
    建议：日索引里直接存摘要；contacts 用增量写。
12. ⬜ `routes/tasks.py` 一次请求里把 `tasks.json` 解析 5 次；`system.py` 的 overview 把 `runs/index.json` 读 2 次。
    建议：请求内读一次往下传。
13. ⬜ `friends.json` 持续累积 base64 头像，且每次 `/api/contacts*` 全量读+解析（当前约 1MB，随好友数线性增长）。
    建议：头像改为按需接口 + 浏览器缓存（`/api/contacts/avatar?name=`），列表响应不再内嵌 base64。

### P2 · 存储并发

14. ✅ **已修** —— `repo` 的 contacts / streak / runs-index 读-改-写全程无锁：工作台点开关与定时任务 `mark_sent_today` 并发会丢更新。
    修法：进程内 `_REPO_LOCK`（RLock）+ `@_serialized` 装饰器，串行化 `upsert_contact` / `remove_contact` /

15. ⬜ **`save_report` 先写 report 再写 index，两次写非原子**。
    ⚠️ 修正一下严重度：**不会导致重复发送** —— 防重依据是发送成功那一刻就写入的

    「当天的统计/连续天数没记上」，会表现为一次误报。建议：index 采用"读-合并-原子写"。
